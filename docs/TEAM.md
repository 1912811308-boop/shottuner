# 专家团编制与协作协议

## 为什么需要分组

这个项目的难点不在"写一个相机界面"，而在于四个互相牵制的领域同时成立：

- 相机参数**能不能写进去**（硬件与系统 API 约束）
- 算法**该写什么值**（成像原理与测光策略）
- 写进去之后**会不会卡**（端侧性能与流水线）
- 用户**看不看得懂**（信息密度与交互）

任何一方单独推进都会产出"能跑但没用"的东西。所以按领域切分，用接口契约锁住边界。

## 团队编制

### 1. 技术负责人（TL）

**职责**：决定平台形态，锁定技术路线，仲裁跨域冲突。

**本项目的关键裁决**：

| 议题 | 结论 | 依据 |
|---|---|---|
| 微信小程序 vs 原生 App | 原生 | 小程序 `camera` 组件无任何曝光参数入口，产品核心功能无法实现 |
| CameraX vs 裸 Camera2 | CameraX + Camera2Interop | 生命周期与设备兼容由 CameraX 兜底，仅有手动参数走 Camera2 通道 |
| 白平衡是否写入 | 只建议不写入 | 手动 R/G/B 增益跨机型差异极大，写入易偏色甚至崩会话 |
| 场景判定用规则还是 CNN | 先规则 | 规则可解释、零延迟、可回归；CNN 需要标注集，列为二期 |

**验收**：任意技术选择必须写出"为什么不是另一个"，否则打回。

---

### 2. 相机系统工程师

**职责**：CameraX 绑定、手动参数下发、能力探测、异常降级。

**交付物**：`camera/CameraEngine.kt`

**核心难题及解法**：

- *难题*：CameraX 的 CaptureRequest 参数在 UseCase 构建时固定，改 ISO 必须重建用例，画面会闪。
  *解法*：变化阈值（ISO 15% / 快门 20%）+ 1.2 秒最小间隔，双闸门控制重建频率。
- *难题*：自动曝光模式下读不到当前参数，闭环无从谈起。
  *解法*：`Camera2Interop.setSessionCaptureCallback` 挂 `onCaptureCompleted`，
  从 `CaptureResult` 取 `SENSOR_SENSITIVITY` 与 `SENSOR_EXPOSURE_TIME`。
- *难题*：部分机型不支持 `CONTROL_AE_MODE_OFF`。
  *解法*：探测 `CONTROL_AE_AVAILABLE_MODES`，不支持则降级纯推荐模式并明示用户。

**验收**：手动写入失败时预览必须仍然可用，不允许黑屏或崩溃。

---

### 3. 成像算法工程师

**职责**：测光特征、场景分类、参数推荐、闭环稳定性。

**交付物**：`analysis/`、`recommend/`、`python/shottuner/`

**核心难题及解法**：

- *难题*：单帧亮度不能直接换算成参数，缺少"当前用什么参数拍的"这个锚点。
  *解法*：把曝光拆成"总量 E = ISO × 快门"与"分配"，用实测参数锚定总量，再做约束分配。
- *难题*：高光溢出后亮度不再线性响应，闭环会过冲。
  *解法*：把 `highlight_clip` 作为独立惩罚项加入 EV 计算，溢出越多压得越狠。
- *难题*：一帧调整到位会引起震荡。
  *解法*：阻尼系数 0.7，并在 Python 侧用 `simulate.py` 做收敛回归。

**验收**：`simulate.py` 中四类场景必须在 16 帧内收敛到 ±0.06 亮度误差。

---

### 4. 端侧性能工程师

**职责**：单帧分析耗时、内存分配、线程模型。

**交付物**：`analysis/FrameAnalyzer.kt`

**核心决策**：

- 只用 `YUV_420_888` 平面直读，全链路零 Bitmap 转换。
- 步长采样到约 160×120 个采样点，统计量精度足够，耗时降到 6ms 以内。
- 分析线程单线程串行 + `STRATEGY_KEEP_ONLY_LATEST`，丢弃积压帧而不是排队。
- 异常全吞：分析器一旦抛异常，CameraX 流水线会永久停摆，这比丢一帧严重得多。

**验收**：中端机 30fps 预览下不掉帧，GC 无明显抖动。

---

### 5. 交互设计

**职责**：信息层级、状态可见性、误操作防护。

**交付物**：`res/layout/`、`MainActivity.kt` 的状态机

**设计原则**：

- 参数区只给四个数字（ISO / 快门 / 色温 / EV），其余全部收进一句提示语。
- 模式必须始终可见："推荐模式 / 自动写入中 / 参数已锁定"三种状态，颜色区分。
- 锁定是一等公民：自动写入下用户随时可能想"就这个参数别动了"，必须一键锁定。
- 任何设备能力缺失都要明示，不能让用户以为"调了没反应"。

**验收**：新用户在不看说明的情况下，30 秒内能说清"现在是什么模式、建议改什么"。

---

### 6. 测试与交付

**职责**：回归用例、构建产物、安装验证。

**交付物**：`python/tests/`、APK、构建脚本

**用例设计原则**：每条断言对应一个真实会翻车的场景，不写"能跑通"式的形式测试。

| 用例 | 防的是什么事故 |
|---|---|
| `test_dark_scene_requests_more_exposure` | 暗场景反向调参 |
| `test_bright_scene_reduces_exposure` | 高光溢出时不压曝光 |
| `test_iso_never_exceeds_cap` | 弱光下 ISO 冲到硬件上限导致噪点崩坏 |
| `test_shutter_respects_scene_bounds` | 快门越界，参数不可执行 |
| `test_action_scene_keeps_fast_shutter` | 抓拍场景把快门放到 1/125 以下 |
| `test_closed_loop_converges` | 闭环震荡不收敛 |
| `test_kelvin_compensates_warm_cast` | 色温补偿方向搞反 |

## 协作协议：接口契约

四个跨域接口，任何一方改动都需要周知：

```
1. FrameStats（性能 → 算法）
   输入：ImageProxy
   输出：直方图、均值、分位、截断比、RGB 均值、饱和度、边缘密度、肤色比
   约束：所有亮度归一化到 0..1；任何字段缺失时用 EMPTY 兜底

2. CameraCaps（相机 → 算法）
   输入：CameraCharacteristics
   输出：ISO 区间、曝光时间区间、是否支持手动、等效焦距
   约束：读不到时返回 UNKNOWN，算法必须能在 UNKNOWN 下工作

3. ManualParams（算法 → 相机）
   输入：iso、shutterNs
   约束：必须落在 CameraCaps 区间内，算法侧负责钳制，相机侧负责容错

4. Recommendation（算法 → 交互）
   输入：上述三者的产物
   输出：场景、目标亮度、EV 偏差、ISO、快门、色温、三脚架建议、两级文案
   约束：文案必须可直接展示，不允许交互层再做数值到语义的翻译
```

## 本轮执行记录

本次交付由我按上述分工串行推进，而非并行拉起六个智能体。原因很实际：
算法与相机两部分强耦合，中间需要反复对齐 `ManualParams` 语义，
拆成并行反而增加沟通成本。

如果后续要并行，最合理的切分点是：

- 相机组独立做「多机型兼容矩阵」（不同厂商对 `AE_MODE_OFF` 的支持差异）
- 算法组独立做「场景分类 CNN 化」，需要先攒一个带标注的数据集
- 两者之间只通过 `FrameStats` 与 `CameraCaps` 两个结构通信，互不影响
